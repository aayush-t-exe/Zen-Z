## 2. Onboarding + personality quiz — CLOSED (6/6 fixed, 1 deliberately left as-is)
- [x] **FIXED — real vulnerability.** `score-personality` had an IDOR: `user_id` came from the request body with no ownership check, and the service-role client bypassed RLS entirely. Any authenticated student could pull (and force a recompute of) any other student's personality scores. Fixed by deriving `user_id` from the caller's verified JWT (`callerClient.auth.getUser()`) instead of trusting the body. Deployed to dev; verified unauthenticated calls now get rejected (401) at the platform gate.
- [x] **FIXED — scoring bug.** `clampScore` treated the scale question's raw `0/5/10` as if already normalized like option weights (~±0.9), so a dimension whose only contributor was the scale question scored the "Ambiverted" (5) and "Extroverted" (10) answers identically (both clamp to 1.0). Fixed in `logic.ts` by normalizing to -1/0/1 before applying the multiplier; added regression tests (34/34 edge-function tests pass, `npx vitest run` in `supabase/functions/`).
- [x] **FIXED** — scoring/save failures were completely swallowed: any failure (answers upsert *or* scoring call) still unconditionally advanced to the recap screen and let the user continue into `(home)`, with no personality_scores ever written — silently bouncing them back to the quiz next session with zero explanation (`getPostAuthRoute` gates on `personality_scores` existing). Now retries the scoring call once, and any real failure keeps the user on the quiz screen with a visible error instead of faking success.
- [x] **FIXED — draft/resume.** Answers previously lived only in local state until one bulk upsert at the very end; killing the app mid-quiz lost everything. Each answer now persists to `personality_answers` as soon as it's given, and a new effect rehydrates in-progress answers on mount, landing the student back on their first unanswered question.
- [x] **FIXED** — empty-questions/fetch-failure state was a dead end (no retry, error text captured but never rendered). Now shows the actual error and a Retry button that re-runs the fetch.
- [x] **FIXED** — no server-side check that `selected_option_ids` in a `personality_answers` row actually belong to that row's `question_id` (RLS lets a student write their own rows directly, so a hand-crafted insert could pull in unrelated dimension weights). `score-personality` now validates option ids against `personality_question_options` for that question before scoring them.
- [ ] **Left as-is, deliberate.** `personality_option_weights`/`personality_scale_mappings` are publicly SELECT-able (`using (true)`) — the full scoring formula is discoverable client-side before answering. Inherent to a data-driven quiz that renders option labels client-side; not worth the complexity to lock down right now.

Verification: `tsc --noEmit` clean, `eslint` clean, `npx vitest run` in `supabase/functions/` — 34/34 pass. `score-personality` redeployed to dev and confirmed rejecting unauthenticated requests. **Not yet deployed to prod** — same "sync at milestone boundaries" pattern as the migrations.

## 3. Profile creation — CLOSED (2 fixed, 1 deferred as a future feature, rest already covered)
- [x] **FIXED — real bug, found live 2026-08-27 while chasing an unrelated-looking 401.** Queried the dev DB directly and found 6 accounts with a real `auth.users` row but **no matching `profiles` row** (predating this session by up to 16 days — not from `delete_own_account()`, which soft-deletes/scrubs but never removes the row and bans the identity rather than leaving it able to sign back in; root historical cause undetermined, but irrelevant to the fix). `handleCreateProfile()` in `profile-creation.tsx` does `.update(...).eq('id', uid)`, assuming `handle_new_user()`'s trigger already created the row — for any account whose profile is missing for any reason, that UPDATE silently matches zero rows and reports success (Postgres/PostgREST don't error on a 0-row UPDATE), and `profiles` has no RLS INSERT policy at all to self-heal through. The student then sails through onboarding into the personality quiz, where `personality_answers.user_id`'s FK to `profiles` finally fails loudly and confusingly (`23503`) — this, not an auth/session problem, is what was actually behind the "Invalid or expired session"-flavored errors chased earlier in Area 1's item 21. Fixed with a narrow `security definer` RPC (`ensure_own_profile()`, `0060_ensure_own_profile.sql`) that mirrors the trigger's own insert (idempotent, `on conflict do nothing`), called right before the update in `handleCreateProfile()`. Backfilled all 6 existing orphaned accounts live so they self-heal on next profile-creation attempt instead of staying stuck.
- [x] Photo upload to private bucket — covered by area 1's dive into `0004_storage_helpers.sql`: bucket is private, RLS scopes upload/read to `<own_uid>/...`, admin views never trust the `photo_url` column as a path (always derive from the authenticated student's own id). No new findings.
- [x] **FIXED** — WhatsApp number had no format validation (client or DB), just non-empty. Founder uses this as a real contact channel for event logistics, so garbage input silently broke that. Added a loose validator (`isValidPhone` in `profile-creation.tsx`) — digits/spaces/dashes/parens only, 7-15 digit count (E.164 range), deliberately not country-restricted since students may be on non-Indian numbers.
- [~] **Deferred, by design — not a bug.** There is no edit-profile screen anywhere in the app (`(home)/profile.tsx` is view-only: photo, emergency contact, sign-out, delete account). Once onboarding is done, a typo'd name/DOB/phone has no in-app fix short of deleting the account and restarting. Flagged to the founder; explicitly left out of this audit as a future product feature, not implemented.
- [x] Date of birth — DB-level CHECK constraints already added in area 1 (`0050_profile_data_integrity_checks.sql`). No new findings.
- [x] No-action, low severity: `gender`/`year_of_study`/`date_of_birth`/`phone` have no DB `NOT NULL`, so a direct API call could null them post-creation — but `getPostAuthRoute` already self-heals this by routing back to profile-creation, so not exploitable for real harm.
- [x] No-action, low risk: photo upload hardcodes `contentType: 'image/jpeg'` regardless of actual file type, but the picker is restricted to `mediaTypes: ['images']` with a forced 1:1 crop, which re-encodes to JPEG in practice on both platforms.

Verification: `tsc --noEmit` clean, `eslint` clean, full `npm run test:db` — all 11 files, 50/50 assertions pass. `0060` migration deployed to dev, 6 orphaned accounts backfilled live.

- [x] Client-reported "success" never trusted alone — `payment.tsx` was already built correctly: it polls the DB-backed `payment_status` after the checkout browser closes rather than trusting any local state, and only `razorpay-webhook` (service-role, signature-verified) is ever allowed to write `payment_status='paid'`. ## 8. Admin dashboard — matching board — CLOSED (2 fixed — one critical, rest already solid)
- [x] **FIXED — critical, systemic photo-identity spoofing.** `apps/admin/lib/photos.ts` blindly trusted the raw `profiles.photo_url` string (joined in via `bookings.profile:user_id(...)`) as a real, fetchable storage path, with zero check that the path actually belonged to that profile. `photo_url` is a self-updatable column (Area 1's `0051_profiles_column_grants.sql` deliberately keeps it self-writable, since students set their own photo at profile creation) — so any student could set their own `photo_url` to another student's real path (`<victim_id>/profile.jpg`) and have the victim's actual photo rendered under the attacker's name across **four** admin pages: `matching/MatchingBoard.tsx`, `reports/page.tsx`, `student/[id]/page.tsx`, `groups/page.tsx`. This undermines the founder's ability to visually identify students at all — a real safety concern for a stranger-matching product, not just a data hygiene issue. The DB-level safe pattern already existed (`get_student_photo_url()`, `admin_student_profiles`/`admin_students_with_personality` in `0004_storage_helpers.sql`, always deriving the path from the *queried student's own id*, never the column) but none of the four admin pages actually used it. Fixed by rewriting `getSignedPhotoUrl`/`getSignedPhotoUrls` to take a student id + `hasPhoto` boolean instead of a path string, always deriving `<id>/profile.jpg` itself (matching the real upload convention in `profile-creation.tsx`), and updated all four call sites to pass id + boolean instead of the raw column value. `photo_url` is now only ever null-checked, never read as a string, anywhere in `apps/admin`.
- [x] **FIXED — hardening, not an active vulnerability (verified empirically before fixing).** `confirm_group()` never explicitly checked the caller was an admin; it relied on the side effect that its own internal payment/status count query is scoped by `bookings`' "own bookings" RLS, so a non-admin could never assemble a *multi*-booking array that passed the count check. Confirmed live that this was NOT exploitable as-is — but also confirmed a min_group_size=1 activity type (nothing in the schema prevents one) lets a non-admin pass every other gate using only their own single booking, which would have succeeded pre-fix. Added an explicit `admin_users` check (`0058_confirm_group_admin_check.sql`), matching every other admin-only RPC/view in the codebase. New pgTAP test (`010_admin_dashboard_security.sql`) proves both: a non-admin is rejected via this exact min-size-1 path, and a real admin is unaffected.
- [x] Founder auth/session on admin site — `login/page.tsx` correctly uses `shouldCreateUser: false` (can't create a new admin account via OTP) and signs out immediately if the authenticated user isn't in `admin_users`. All 7 admin pages (`page.tsx`, `analytics`, `groups`, `matching`, `reports`, `student/[id]`, `venues`) consistently gate on `useAdminGuard()` — no page found unguarded. `middleware.ts` is a no-op (`matcher: []`); RLS is the actual enforcement layer, matching its own inline comment.

- [x] Authorization: non-admin cannot hit admin-only RPCs — see the `confirm_group()` finding above; also confirmed `groups`/`group_members` have no non-admin INSERT policy (`0001_init.sql`'s `"admin manage groups"` is the only write policy, `for all using (...)` with no separate insert path).

## 11. Razorpay → PayU cutover — 2026-08-29 — CODE REWRITTEN AGAINST REAL PAYU DATA, NO DEV/PROD DEPLOY YET
- [x] **Sandbox spike done — against real PayU, not just docs.** Ran a real OAuth token request, a real Payment Link creation, and a real ₹1 live payment end-to-end, and captured the actual webhook PayU delivered. Findings that corrected the original guess-based implementation:
  - Auth is **OAuth2 client-credentials** (`accounts.payu.in`/`uat-accounts.payu.in` → bearer token), not the classic key+salt hash the first draft assumed.
  - The `merchantId` header wants the **numeric MID** (shown in the dashboard header, e.g. `13750905`), not the alphanumeric Merchant Key — using the Merchant Key silently returned an empty `200 OK` with no error, which cost real time to track down.
  - Amount goes in **`subAmount`** (rupees, not paise) with `isAmountFilledByCustomer: false` — not a plain `amount` field.
  - **No redirect ever happens.** A real live payment stayed on PayU's own "Payment Completed" page with no continue button — `successUrl`/`failureUrl` appear to be accepted but not acted on for this product. Confirms the DB-lookup redirect-bridge design (rather than trusting anything passed back) was the right call, though in practice `payment.tsx`'s poll-after-browser-closes is now known to be the *only* real path back into the app, not a fallback.
  - The webhook is form-urlencoded, registered once per event type in the dashboard (not per-request). Its signature is `sha512(salt|status|udf10|udf9|...|udf1|email|firstname|productinfo|amount|txnid|key)` — **confirmed byte-for-byte against the real captured hash.** PayU's docs only ever show a 5-udf version of this formula; the real payload carries udf1-udf10 and the reverse hash needs all ten, so the 5-udf version (what the first draft had) computes a completely different, wrong hash.
  - PayU mints its **own `txnid`** per attempt, unrelated to anything we send — it cannot be used to match a webhook to a booking. **`udf1`** is the only value we control that's reliably echoed back, so it's the sole correlation key; **`mihpayid`** (PayU's permanent transaction id) is what gets stored as the booking's `payment_id` once paid.
